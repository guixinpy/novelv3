# 04 · 开发规则与约束

> **最后更新**: 2026-06-06
> **版本**: v1.0
> **前置阅读**: [01-愿景与架构目标](./01-vision.md)
> **重要性**: ★★★★★（每次动手前必读）

---

本文档定义了 codex 在 novelv3 项目上开发时必须遵守的工程规范。这些规则不是"建议"，而是项目长期稳定性的保障。

---

## 一、编码前检查清单

每次开始写代码前，codex 必须确认以下事项：

```
□ 1. 我理解这个任务在 [05-进度追踪](./05-progress-tracker.md) 中的位置吗？
□ 2. 我知道这个改动会影响哪些模块吗？（查 [02-模块清单](./02-module-inventory.md)）
□ 3. 我有明确的"完成标准"吗？（可验证的输出/测试用例）
□ 4. 这个改动需要更新 trace/审计吗？（见 §二.2）
□ 5. 这个改动影响世界模型吗？如果影响，需要通过提案审批吗？（见 §二.3）
□ 6. 有现成的参考模式可以用吗？（查 [03-参考模式](./03-reference-patterns.md)）
□ 7. 我需要先写测试吗？（见 §三）
□ 8. 我是否正在触碰巨型文件或复杂投影？如果是，是否已有拆分/止血方案？（见 §二.7）
```

## 二、架构约束（不可妥协）

### 2.1 AI 不得直接修改世界真相

任何对 Athena 世界模型的修改，必须走提案→审阅→通过/拒绝流程。不允许绕过 `WorldProposalBundle` 直接写入事实。

**检查方法**：搜索代码中是否有直接 INSERT/UPDATE `world_fact_claims` 或类似表的操作。如果有，必须改为走提案流程。

### 2.2 新增 AI 调用必须接入 Trace

每次新增调用 LLM 的代码，必须同时：
1. 创建 `AIModelCallTrace` 记录
2. 记录 context blocks（提示词中包含的上下文来源）
3. 记录调用结果（成功/失败/错误信息）

**检查方法**：新增的 LLM 调用点必须能从前端的 ModelTraceDrawer 中看到。

### 2.3 新增数据库字段必须完整铺开

新增任何数据库字段，必须同时修改：
1. SQLAlchemy model（`backend/app/models/`）
2. Pydantic schema（`backend/app/schemas/`）
3. Alembic migration（生成新的 migration 文件）
4. 前端 API 调用和状态管理（如该字段暴露给前端）
5. 相关测试

**检查方法**：搜索新字段名在整个 codebase 中的出现位置，确认所有必要位置都已更新。

### 2.4 新增生成链路必须考虑失败路径

任何新增的生成类功能，必须考虑：
1. 失败时的 trace 记录
2. 用户可见的错误信息
3. 恢复路径（能否重试？能否回滚？）

**检查方法**：模拟该功能失败时的行为（异常、超时、模型返回格式错误等）。

### 2.5 前端异步加载必须处理 project scope

前端涉及异步请求的组件，必须：
1. 使用 requestId 和 project scope version
2. 处理迟到请求（旧数据不覆盖新项目数据）
3. 组件销毁时取消未完成的请求

**参考**：frontend/src/stores/ 中的 worldModel store 的 request lane 实现。

### 2.6 不得绕过 Hermes 的流程控制

新增操作必须考虑项目当前状态是否允许执行。例如：
- 不能在没有设定时生成正文
- 不能在没有大纲时执行章节生成
- 不能重复触发正在运行中的生成任务

### 2.7 前端 Agent Run 投影必须优先拆分

`AgentRunDrawer.vue` 已是 7000 行级风险文件。新增 Frontend Agent UX 投影时，必须遵守 ADR-010：

1. Drawer 只作为 Shell：负责 run/step 基础状态、工具输出定位、通用操作和挂载面板。
2. 每个复杂工具投影优先写成独立 Panel 组件，Panel 内只展示安全摘要，不渲染 raw output。
3. Drawer 集成测试只验证面板能被正确挂载；字段脱敏、标签、计数和边界数据由 Panel 专属测试覆盖。
4. 若一次改动会向 `AgentRunDrawer.vue` 或 `AgentRunDrawer.test.ts` 新增超过约 50 行投影逻辑，必须先拆 Panel 或说明为什么不能拆。
5. 触碰超过 1500 行的文件时，不做顺手扩张；如果改动点属于可迁出的局部投影，应优先迁出或至少做到主文件低净增长。

**检查方法**：提交前记录相关文件行数和 diff stat；确认新增复杂投影有独立组件/测试，且未继续把解析、脱敏和模板大段堆进 Drawer。

## 三、测试规则

### 3.1 测试金字塔

```
         ┌──────┐
         │ UAT  │  手工验收（真实小说生成验证）
         ├──────┤
         │ E2E  │  longform smoke + 关键用户路径
         ├──────┤
         │ 集成  │  API 测试 (pytest) + 组件测试 (vitest)
         ├──────┤
         │ 单元  │  核心逻辑函数测试
         └──────┘
```

### 3.2 什么时候必须写测试

| 场景 | 必须写 | 测试类型 |
|------|--------|---------|
| 新增 API 端点 | ✅ | pytest 集成测试 |
| 新增 Agent 工具 | ✅ | pytest + 工具契约测试 |
| 新增前端组件 | ✅ | vitest 组件测试 |
| 修改核心逻辑 | ✅ | pytest 单元测试 |
| 修复 bug | ✅ | 先写复现测试 |
| 重构（行为不变） | 跑现有测试 | 无需新增 |
| 纯配置变更 | ❌ | 无需 |

### 3.3 运行测试的命令

```bash
# 后端测试
cd backend && .venv/Scripts/python -m pytest tests/ -q

# 前端测试
cd frontend && npm run test

# 完整验证
cd frontend && npm run build   # 含 vue-tsc + vite build
cd backend && .venv/Scripts/python -m pytest tests/ -q

# 长篇规模 smoke
.venv/Scripts/python scripts/longform_scale_smoke.py
```

### 3.4 测试先行原则（TDD 适用场景）

对于以下场景，必须先写失败的测试再实现：
- 新增 API 端点
- 新增 Agent 工具或命令
- 修复明确可复现的 bug
- 修改核心业务逻辑

## 四、代码风格

### 4.1 通用原则

1. **匹配现有风格**：新代码应与周围代码的风格一致，即使你认为有更好的写法
2. **不过度抽象**：不为单次使用的代码创建抽象层
3. **不过早优化**：不在没有性能数据的情况下做性能优化
4. **注释解释"为什么"**：不描述"做了什么"（代码本身已说明）

### 4.2 Python 后端

- 使用 `black` + `ruff` 格式化
- 类型注解在函数签名中
- Service 层逻辑不在 API 路由中写
- 工具实现遵循 descriptor + adapter + execution 三层模式

### 4.3 TypeScript/Vue 前端

- 使用 ESLint + Prettier
- Pinia store 按领域分离
- 组件遵循 Vue 3 Composition API
- API 调用集中在 `frontend/src/api/`

## 五、文档更新规则

### 5.1 必须更新文档的场景

| 场景 | 需要更新的文档 |
|------|---------------|
| 完成一个开发阶段 | [05-进度追踪](./05-progress-tracker.md) |
| 新增/删除/重构模块 | [02-模块清单与状态](./02-module-inventory.md) |
| 做出影响架构的决策 | [06-架构决策记录](./06-architecture-decisions.md) |
| 从参考项目中吸收新模式 | [03-参考项目模式映射](./03-reference-patterns.md) |
| 发现文档与实际情况不符 | 立即修正相关文档 |
| 项目目标或范围变更 | [01-愿景与架构目标](./01-vision.md) |

### 5.2 文档维护原则

- **确保永不过期**：每次 session 结束前检查进度文档是否更新
- **删除而非标记**：过期的内容删除，不要标记 `[已废弃]`
- **归档到 docs/archive/**：历史材料移到归档目录
- **最后更新时间戳**：每个文档底部有更新日期

## 六、Git 规则

### 6.1 Commit 规范

- **粒度**：一个 commit 对应一个逻辑变更
- **消息格式**：英文，简洁描述（参考已有的 commit history）
- **末尾追加**：`Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`

### 6.2 Branch 规范

- 从 `main` 分支创建 feature branch
- 命名：`codex/<feature-name>` 或 `<type>/<description>`
- 当前开发分支：`codex/narrative-memory-activation`

### 6.3 PR 规范

- PR 描述应包含：改动目的、改动范围、测试结果
- PR body 末尾追加：`🤖 Generated with [Claude Code](https://claude.com/claude-code)`

## 七、禁止事项

### 禁止的代码行为

1. ❌ **绕过提案直接写入世界模型**（违反 §二.1）
2. ❌ **新增 LLM 调用不接 Trace**（违反 §二.2）
3. ❌ **只改 model 不改 migration**（违反 §二.3）
4. ❌ **在 API 路由中写业务逻辑**
5. ❌ **删除或修改已有测试而不确认**
6. ❌ **引入新的外部依赖而不说明理由**
7. ❌ **静默失败**——所有异常必须记录或传播
8. ❌ **硬编码值**——配置项应放在配置文件中

### 禁止的设计行为

9. ❌ **为"未来可能的需求"添加抽象层**
10. ❌ **重构与当前任务无关的代码**
11. ❌ **在没有真实问题触发的情况下，因为"参考项目有"而添加功能**
12. ❌ **一次性铺开全套架构**——增量演进
13. ❌ **继续向巨型 Drawer 堆复杂投影**——新增复杂投影必须先按 ADR-010 拆成 Panel

## 八、完成标准

一个开发任务被认定为"完成"，必须满足：

```
□ 所有测试通过（pytest + vitest + build）
□ 新增功能有测试覆盖
□ 新增 AI 调用有 trace 记录
□ 文档已更新（至少进度追踪已更新）
□ 代码已 self-review（检查上述禁止事项）
□ 提交的 commit 消息清晰描述了改动
```

对于涉及 Agent 行为变更的任务，额外要求：

```
□ 至少一次真实生成验证（手动运行一次章节生成/审稿等）
□ 验证结果记录在进度追踪中
```
